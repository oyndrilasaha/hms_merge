# St George Hospital Management System — MVP architecture

## Purpose and boundary

This repository is an assessment MVP: it demonstrates a complete, auditable hospital workflow with synthetic data. It is not a production clinical system and must not store real patient information.

The MVP deliberately uses only the Node.js 24 standard library. The browser client is plain HTML, CSS and JavaScript; the server uses the built-in HTTP, cryptography and SQLite modules. This keeps setup repeatable and avoids third-party package risk during assessment. A production release would require a hardened deployment platform, MySQL, managed secrets, TLS termination, monitoring, backup automation and a formal security/privacy review.

## Runtime view

```text
Browser / installable PWA
        |
        | same-origin HTTPS in production; HTTP on local demo only
        v
Node.js HTTP server
  - static-file/PWA delivery
  - JSON API router
  - authentication and session checks
  - role/branch authorisation
  - validation and workflow services
  - audit recording
        |
        v
SQLite database (local MVP)
  - synthetic seed records
  - transactional operational data
  - append-oriented audit events
```

The client never connects directly to the database. Every sensitive decision is repeated on the server; hiding a button is usability, not access control.

## Logical components

| Component | Responsibility | Trust boundary |
|---|---|---|
| PWA shell | Responsive navigation, forms, status messages, cached application shell | Untrusted client input |
| API router | Method/path matching, JSON parsing, response shape and error handling | Internet-facing boundary |
| Authentication | Password verification, session creation, inactivity expiry and logout | Security-critical |
| Authorisation | Role permission and branch/patient-scope checks | Security-critical |
| Domain services | Patient, appointment, clinical, laboratory, pharmacy, billing and dashboard rules | Business-integrity boundary |
| Persistence | Prepared SQL, transactions, indexes, schema and seed data | Data-integrity boundary |
| Audit service | Actor/action/object/outcome/time records for security and material changes | Accountability boundary |

## Main workflow

1. A seeded user signs in and receives an opaque server-side session.
2. A receptionist registers a synthetic patient and books an available doctor.
3. Conflict checks reject overlapping appointments for that doctor.
4. A doctor appends a clinical note and creates a laboratory order.
5. A laboratory technician releases a result.
6. A pharmacist dispenses valid stock; the transaction reduces inventory.
7. Billing records or updates an invoice.
8. The dashboard and audit view show scoped operational evidence.

Each implemented write is intended to be validated, authorised and audited; the negative permission and audit-completeness tests must verify that claim. Multi-step inventory and appointment operations should execute in a database transaction so a partial result cannot be committed.

## SQLite MVP decisions

- The database is a local file created from a versioned schema and deterministic synthetic seed data.
- Foreign keys are enabled and identifiers are generated by the server/database.
- Prepared statements are required for all user-controlled values.
- Date/time values use an unambiguous UTC representation; the UI converts them for display.
- Appointment and inventory writes use transactions. An application conflict query protects the demo; the production schema must also use database constraints/locking appropriate to MySQL.
- The database file and generated runtime data are not source evidence and should not be committed.

SQLite is appropriate for a single-process demonstration. It does not prove NFR2 (200 concurrent users), NFR6 (multi-server deployment), NFR16 (99.5% availability), NFR17 (scheduled backups) or NFR18 (30-minute recovery).

## Production MySQL migration

The target SRS architecture remains PHP/MVC services with MySQL; this Node/SQLite build is a working executable prototype used to validate workflows and requirements. Production migration should preserve API contracts and separate domain services from SQL-specific persistence.

Recommended migration sequence:

1. Freeze the approved schema and create repeatable MySQL migrations.
2. Map SQLite types to MySQL types explicitly: timestamps, booleans, monetary decimals, JSON and generated identifiers.
3. Replace SQLite-specific SQL and transaction behaviour with a MySQL repository implementation.
4. Add composite indexes for patient/branch searches, doctor appointment time ranges and status/date reporting.
5. Use MySQL transactions plus row or advisory locking to prevent concurrent appointment and stock races.
6. Move sessions to a shared, expiring store before adding multiple application instances.
7. Keep documents outside the public web root in protected object storage; store only metadata/references in MySQL.
8. Import synthetic data first, reconcile row counts and totals, and run the same contract/integration tests.
9. Add managed TLS, secrets, encryption keys, monitoring, immutable audit retention, encrypted backups and restore drills.
10. Complete privacy, threat-model, penetration, accessibility, performance and disaster-recovery assurance before any real-data use.

## Architectural limitations to state in demonstrations

- Local HTTP is for demonstration only; NFR9 requires HTTPS/TLS in deployment.
- A single Node process and SQLite file do not demonstrate scale or high availability.
- Seeded notifications and payments, if displayed, are workflow simulations—not real SMS/email or gateway processing.
- The MVP provides only the implemented subset recorded in `REQUIREMENTS_TRACEABILITY.md`.
- Proposed FR49–FR64 are not part of the approved baseline unless written supervisor/stakeholder approval is recorded.
